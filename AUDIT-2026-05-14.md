# WallDecor Portal Production Audit — 2026-05-14

Scope: P0/P1 readiness for the live VPS/MySQL service before inviting real users.

Assumptions:
- VPS is a copy of GitHub `main`.
- Production database is MySQL, using `deploy/schema.mysql.sql`.
- SQLite is only a local development convenience.
- Old `AUDIT.md` and `PROJECT_STATE_REVIEW.md` are historical inputs, not trusted without code verification.

Priority scale:
- P0: security, data loss, unauthorized access, or incorrect money movement.
- P1: core business flow broken or blocks launch.
- P2: workflow/UX issue or technical debt that can wait briefly.
- P3: cleanup, lint, polish.

## Findings

### F-001 — CSV import writes `project_items.created_at`, but MySQL production schema has no such column

- Priority: P1
- Area: MySQL schema / CSV import
- Evidence: `deploy/schema.mysql.sql` defines `project_items` without `created_at`; `src/app/actions/import.ts` inserts into `project_items (..., created_at)` when `importedAt` is supplied.
- Impact: CSV import with an import date fails in production MySQL, blocking admin data migration/import.
- Fix: Do not write `project_items.created_at` unless the production schema owns that column. Project-level `created_at` is enough for the current UI/reporting.
- Status: fixed in this branch

### F-002 — Wallet page uses SQLite-only `datetime('now', '-90 days')` against MySQL

- Priority: P1
- Area: MySQL compatibility / architect wallet
- Evidence: `src/app/dashboard/wallet/page.tsx` queries payout history with `created_at >= datetime('now', '-90 days')`; `preprocessSQL()` only converts MySQL syntax to SQLite, not SQLite syntax to MySQL.
- Impact: Architect wallet page can crash in production MySQL when loading payout history.
- Fix: Use portable project convention: `DATE_SUB(NOW(), INTERVAL 90 DAY)`.
- Status: fixed in this branch

### F-003 — HOLD payout action updates missing `payout_requests.updated_at`

- Priority: P1
- Area: MySQL schema / admin payout workflow
- Evidence: `src/app/actions/admin.ts` runs `UPDATE payout_requests SET status = 'HOLD', updated_at = CURRENT_TIMESTAMP`, but `deploy/schema.mysql.sql` has no `updated_at` on `payout_requests`.
- Impact: Admin cannot put payout requests on hold in production MySQL.
- Fix: Update only `status` for HOLD; final processing timestamps remain handled by `updatePayoutStatus()`.
- Status: fixed in this branch

### F-004 — Manual architect welcome email has wrong placeholders

- Priority: P1
- Area: Onboarding / email
- Evidence: `ARCHITECT_REGISTERED` template needs `{{email}}`, `{{password}}`, `{{portal_url}}`; `main` passes `password` and `site_url`, but not `email` or `portal_url`.
- Impact: New architects do not receive a complete login email, and manager sees success even if the send path fails.
- Fix: Send the exact `ARCHITECT_REGISTERED` placeholders (`email`, plaintext temporary password, `portal_url`), surface email-send failures in the registration modal, and cover placeholder generation with a regression test.
- Status: fixed in this branch

### F-005 — STAFF can execute payout and cashback financial actions

- Priority: P0
- Area: RBAC / financial operations
- Evidence: `updatePayoutStatus()`, `handlePayoutRequest()`, `/api/admin/payouts/batch`, and `issueDiscountCode()` accept `STAFF`; `PRODUCT_BRIEF.md` says STAFF cannot execute financial payouts or configuration.
- Impact: A STAFF account can mark payouts paid/rejected and issue cashback card codes, causing unauthorized money movement.
- Fix: Require `ADMIN` for payout status changes, batch payouts, and cashback card issuing. Keep STAFF read/status workflow access where appropriate.
- Status: fixed in this branch

### F-006 — STAFF can mutate email templates through server actions

- Priority: P1
- Area: RBAC / configuration
- Evidence: `/dashboard/admin/settings/emails` page is ADMIN-only, but `getEmailTemplates()`, `updateEmailTemplate()`, and `testEmailTemplate()` server actions allow STAFF.
- Impact: STAFF can bypass the page and modify/test operational email configuration.
- Fix: Require `ADMIN` inside the server actions too.
- Status: fixed in this branch

### F-007 — STAFF user-management permissions need an operational/admin split

- Priority: P1
- Area: RBAC / user management
- Evidence: STAFF is expected to register architects and operate projects, but not manage financial settlement or system configuration.
- Impact: If STAFF is too restricted, managers cannot onboard architects or move projects through the operational pipeline; if too broad, STAFF can affect payouts/settings.
- Fix: Allow STAFF to register architects, add projects, assign/caretake projects, and change project status through the operational pipeline. Keep architect profile edit, password reset, account deletion, payouts, cashback code issuing, and settings/template changes ADMIN-only.
- Status: fixed in this branch

### F-008 — Production dependencies include high Next.js advisories

- Priority: P1
- Area: dependency security
- Evidence: `npm audit --omit=dev --audit-level=high` reported high-severity advisories against `next@16.1.6`.
- Impact: Live service would run a framework version with known request handling, cache, CSRF, XSS, SSRF, and middleware/proxy advisories.
- Fix: Upgrade `next` and `eslint-config-next` to `16.2.6`; upgrade direct `uuid` dependency to `14.0.0`.
- Status: fixed in this branch; production audit now has no high-severity findings, with moderate transitive advisories still reported by npm.

### F-009 — Admin backup exports the wrong cashback table

- Priority: P1
- Area: backup / recovery
- Evidence: `/api/admin/backup` exported `discount_cards`, which does not exist in the production schema, but did not export `cashback_redemptions`.
- Impact: MySQL JSON backups omit cashback card redemption history, which weakens financial recovery/auditability.
- Fix: Export `cashback_redemptions`; use a controlled JSON table export for both MySQL production and SQLite development.
- Status: fixed in this branch

### F-010 — Final payout action stored `APPROVED` instead of `PAID`

- Priority: P1
- Area: admin payouts / final settlement
- Evidence: `handlePayoutRequest()` mapped both `APPROVE` and `PAID` to `APPROVED`; `/api/admin/payouts/batch` also finalized selected payouts as `APPROVED` while the UI says "wypłać"/"Zapłacona".
- Impact: Admin could not reliably mark the last settlement phase as paid; `PAYOUT_PROCESSED` email only sends for `PAID`, and admin payout state could diverge from the financial reality.
- Fix: Centralize payout action-to-status mapping, persist `PAID` for the final paid action, make batch payouts use `PAID`, and allow legacy `APPROVED` requests to move to `PAID`.
- Status: fixed in this branch

### F-011 — Cashback card redemption was not atomic

- Priority: P1
- Area: cashback wallet / discount card redemption
- Evidence: `requestRedemption()` called `spendCashback()` before inserting `cashback_redemptions`, using separate database writes without a transaction.
- Impact: If the redemption insert failed after wallet spend rows were inserted, the architect could lose cashback balance without a pending card request for admin to process.
- Fix: Allow `spendCashback()` to run on a transaction-bound query function and wrap wallet spend plus redemption insert in one transaction.
- Status: fixed in this branch

### F-012 — Payout status updates were multi-step without transaction safety

- Priority: P1
- Area: admin payouts / financial consistency
- Evidence: `updatePayoutStatus()` updated `payout_requests`, linked `commissions`, and wallet spend side effects as separate writes; batch payout also auto-rejected a request after a processing error.
- Impact: A database or wallet-spend failure could leave payout, commission, or cashback state out of sync. Batch errors could incorrectly reject a payout request that only hit a technical processing failure.
- Fix: Wrap payout status mutation, linked commission mutation, and cashback spend in one transaction. Batch payout now records per-request errors without converting them to `REJECTED`.
- Status: fixed in this branch

### F-013 — Commission payout accepted partial amounts while locking whole commission rows

- Priority: P1
- Area: architect commission payout / financial consistency
- Evidence: `requestCommissionPayout()` accepted any requested amount up to the total earned commission, then selected whole `commissions` rows until the requested amount was covered and attached all selected rows to one payout.
- Impact: A crafted server-action call could request less than the available commission, lock a larger whole commission row, and later mark the full row paid under a smaller payout amount.
- Fix: Because the current model does not split commission rows, require commission payout requests to match the full currently available earned commission amount.
- Status: fixed in this branch

### F-014 — Cashback expiry dates used ISO strings that can fail on MySQL TIMESTAMP

- Priority: P1
- Area: MySQL compatibility / cashback wallet
- Evidence: project finalization and item corrections wrote `expires_at` with `Date.toISOString()`, e.g. a value with `T` and `Z`, into a MySQL `TIMESTAMP` column.
- Impact: strict production MySQL can reject cashback creation during project completion or corrections.
- Fix: Format application-generated SQL datetimes as `YYYY-MM-DD HH:mm:ss` before writing `expires_at`.
- Status: fixed in this branch

### F-015 — Backup omitted project file metadata

- Priority: P1
- Area: backup / recovery
- Evidence: `/api/admin/backup` exported business tables but did not include `project_files`, while project file metadata is stored in the production schema.
- Impact: restoring from backup would lose project-to-file metadata and make uploaded files difficult to reconcile.
- Fix: Include `project_files` in the backup table list.
- Status: fixed in this branch

### F-016 — Google sign-in auto-created invite-less architect accounts

- Priority: P1
- Area: onboarding / access control
- Evidence: the Google auth callback inserted a new `ARCHI` user whenever a Google email did not already exist.
- Impact: the portal was not invite-only; any Google account could create an architect account and submit projects.
- Fix: Google sign-in now links only existing users and rejects unknown emails.
- Status: fixed in this branch

### F-017 — Architect project detail page exposed projects by ID

- Priority: P1
- Area: access control / project confidentiality
- Evidence: `/dashboard/projects/[id]` loaded project details and file metadata by `projectId` before checking that the current `ARCHI` owned the project.
- Impact: a logged-in architect who learned another project UUID could view project/client/amount/commission details and file metadata.
- Fix: enforce `project.owner_id === session.user.id` for `ARCHI` before loading files or rendering details.
- Status: fixed in this branch

### F-018 — Non-ARCHI owners could receive project commissions

- Priority: P1
- Area: RBAC / financial consistency
- Evidence: `createProject()` accepted arbitrary `ownerId` from ADMIN/STAFF without verifying that the owner was an architect; `requestCommissionPayout()` only required a logged-in session.
- Impact: a STAFF account could create/complete a project on a non-architect account and create a commission payout obligation.
- Fix: project owners must be `ARCHI`, and commission payout requests are restricted to `ARCHI`.
- Status: fixed in this branch

### F-019 — STAFF could edit payout invoice metadata despite read-only payout access

- Priority: P1
- Area: RBAC / payout metadata
- Evidence: `updatePayoutInvoiceNumber()` accepted STAFF, and the payout queue rendered an editable invoice-number field even when the queue banner said read-only.
- Impact: STAFF could mutate payout records even though payout handling is ADMIN-only.
- Fix: invoice number updates now require financial permissions (`ADMIN`), and STAFF sees the value read-only.
- Status: fixed in this branch

### F-020 — Cashback balance subtracted spends from expired earning buckets

- Priority: P1
- Area: cashback wallet / balance accuracy
- Evidence: `getArchitectStats()` and admin wallet summaries ignored expired `EARN` rows but still subtracted `SPEND` rows linked to those expired rows.
- Impact: after partial use of a cashback bucket that later expired, the wallet could show too low or negative balance and block valid redemption from other active buckets.
- Fix: centralize wallet balance SQL around active earning rows and subtract only spend/expire rows linked to those active buckets.
- Status: fixed in this branch

### F-021 — Concurrent commission payout requests could lock the same earned rows

- Priority: P1
- Area: architect commission payout / race protection
- Evidence: `requestCommissionPayout()` selected `EARNED` commissions, then later updated them without checking they were still `EARNED`.
- Impact: parallel submits could create duplicate payout requests against the same earned commission rows.
- Fix: commission locking now updates only rows still in `EARNED` status and aborts the transaction if any expected row was already taken.
- Status: fixed in this branch

### F-022 — Concurrent cashback spend could overdraw the same earning bucket

- Priority: P1
- Area: cashback wallet / race protection
- Evidence: `spendCashback()` selected active earning rows and then inserted spend rows; without row locks, two redemption transactions could both see the same remaining balance.
- Impact: parallel cashback redemptions could spend more than the available wallet balance.
- Fix: active earning rows are selected `FOR UPDATE` in MySQL transactions; SQLite development strips the clause because SQLite write transactions already serialize writes.
- Status: fixed in this branch

### F-023 — Concurrent project finalization could double-create base cashback/provision rows

- Priority: P1
- Area: project finalization / race protection
- Evidence: project completion used random IDs for base `EARNED` commission rows and cashback `EARN` wallet rows, so concurrent finalization could insert duplicates for the same item.
- Impact: duplicate cashback and potentially duplicate base commission could be credited for one project item.
- Fix: base project-finalization commission and cashback grants now use deterministic item-based IDs, making concurrent duplicate inserts fail instead of double-crediting.
- Status: fixed in this branch
